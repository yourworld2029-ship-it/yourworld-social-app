---
name: Long-video compression fallback
description: Browser-file compression and safe chunked fallback for horizontal and vertical Long Videos.
---

The project Storage bucket cap is 500 MB. Long Videos below that cap may use optional MP4 compression only when they are at most 300 MiB and five minutes; if that optional work is unfinished at submit, preserve the immediate original/resumable upload path. Files at or above 500 MB must finish tiered compression before any upload attempt, and the encoded result must be smaller than its source and strictly below the cap. The large-file tier targets about 70–100 MB. If required compression fails or cannot meet the cap, fail clearly rather than sending the original to Cloudflare or Supabase. Retry a recognizable storage size-limit rejection once using a compressed blob; do not retry auth or network errors this way. `MediaRecorder` has no CRF setting, so size goals must be estimated with a duration-based bitrate; validate fast-start layout and audio preservation. Keep TUS chunks at 6 MiB, use the local selected file for the pending feed preview, and report actual transferred-byte counts only for Long Video. Keep Reels behavior unchanged.

**Why:** The user specified a 500 MB project Storage limit. Oversized originals must never reach a bucket, while making under-limit uploads wait for optional transcoding would unnecessarily delay normal TUS uploads. `MediaRecorder` exposes bitrate rather than CRF, and hardware encoder/resource failures vary across Android devices.

**How to apply:** Start mandatory compression asynchronously during file selection so the user can edit metadata. When an over-limit upload is submitted before compression finishes, keep the background task alive and await the result; reject it if the output is not under the cap. For under-limit files, abort unfinished optional compression and start the existing resumable path. Retry only explicit storage-size failures with a smaller compressed blob. Do not change Reel behavior as part of Long Video work.
